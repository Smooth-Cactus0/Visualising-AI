## As built
_Kept up to date by Claude._
### Overview
Interactive web pages, with no build step, that show what the boxes in a deep-learning architecture diagram actually compute. Three pages exist, all for the same toy CNN: a 2D page (convolution one output cell at a time, ReLU, pooling, channels, receptive field, through to a prediction), a 3D page (the same network drawn as H×W×C blocks with three.js, with kernel sweeps and receptive-field cones), and a training page (real MNIST digits shrunk to 16×16 stream in; one SGD step is shown in full, forward, loss, backward, update, then the arc of many with curves, kernels over time and accuracy on held-out digits; weights trained there load into the other two pages). The repo's CLAUDE.md says: "Purpose: interactive, visual explanations of how DL architectures compute (CNN first; ViT, ConvNeXt, CoAtNet next). The audience is someone who uses these models daily and wants the concrete steps behind diagrams like 'Conv 3×3 → ReLU → MaxPool → … → FC'." Alexy, 2026-10-12: the project is to "visualise different models, starting with DL", ported locally "to add to it without being limited by artifacts size, versioning and such."

### Method
- Plain HTML plus ES modules, served statically. GitHub Pages deploys the repo root from `main` (`.github/workflows/pages.yml`). Local run: `python -m http.server 8000` from the repo root (modules need http, not file://); maths test: `node core/cnn.test.mjs`.
- Toy network: 16×16×1 input → conv1 (4 hand-picked 3×3 kernels: Sobel-x, Sobel-y, Laplacian, diagonal; stride, padding and dilation selectable) + ReLU → 2×2 pool (max or average, a toggle on both pages) → conv2 (8 random 3×3×4 kernels) + ReLU → 2×2 pool → global average (8 values) → FC 8×10 (random) → softmax over 10 classes. The 2D page can also switch the activation off. Nothing is trained; the pages say so wherever a prediction appears.
- `core/cnn.js` holds the forward pass, pooling, softmax, receptive-field propagation and the kernel and input presets, as pure functions with a test. Both pages are ES modules (`<script type="module">`) that import it; each keeps only display code plus two thin wrappers: the 2D page builds the zero-padded input it draws in stage 2, and both pages resolve the head probes (a global-average entry, a class, a score, an input pixel) before calling the core `footprint`. `forward` takes `activation: 'relu' | 'none'` (the 2D ReLU toggle) and `poolMode: 'max' | 'avg'`; `footprint` takes one cell `{stage, r, c, ch}` or a region `{stage, rect, ch | chs}`.
- Interaction grammar shared by every page: yellow = forward kernel window, green = receptive field traced backward; hovering any cell highlights its receptive field in every upstream tensor; technical terms get a dotted inline definition plus a Terms section on both pages. The 3D readout for a pooled cube writes out the 2×2 block it summarises, as the 2D page does. At the head, both pages show only the direct link: a global-average entry lights its pool-2 map, an FC weight lights its average and its class, a class lights the 8 averages and its column of W; the cone back to the input is not drawn there.
- `ui/terms.js` and `ui/terms.css` hold the terms mechanism (the `TERMS` array, the dotted definitions with their tooltip, the Terms section); both pages import `installTerms` with their own text selectors. Terms are linked at their first mention per paragraph, in order of appearance; dynamic text (readouts, the sweep hint) is left unlinked.
- 3D depth layout: the default "whole network" camera looks from high up and nearly head-on from the input end, so the stages recede as a staircase and the input hides nothing; chosen from headless-Edge screenshots of nine candidate presets at two window widths.
- `core/train.js` holds the training maths as pure functions: `gradFootprint`, the backward mirror of the receptive field (which later gradient cells a gradient value is a sum over, up to the scores); cross-entropy loss; the backward pass (scores p − y → FC → global average, a 16th to each cell → pool routing, max to the first maximum or average spread → ReLU gate → conv kernel and input gradients at stride 1, pad 1); He-uniform initialisation (±√(6/fan_in), seeded, or the hand-picked bank for layer 1); one SGD step; batch averaging; prediction; accuracy; a seeded shuffled order. `core/data.js` reads `data/mnist16.bin`: 3,000 training and 1,000 test MNIST digits, 300 and 100 per class, area-resampled from 28×28 to 16×16 by `tools/make_mnist16.py` (standard-library Python, seed 1; format and CC BY-SA 3.0 attribution in `data/README.md`).
- Training page `cnn-train/`. Band 1, One step: a phase strip digit → forward → back: FC → back: layer 2 → back: layer 1 → update; Step runs one phase, Next digit finishes the digit and brings the next. The gradient is computed in one go when the backward pass starts and revealed a layer at a time from the loss towards the input; each backward step frames in green what it computed and lights its arrows, and cells not computed yet are drawn faint in place so nothing moves between phases. In 2D the whole network is one line in a horizontally scrolling frame (fits a window of about 1600 px), laid out as the data flows with each layer's weights between the map they read and the map they make (layer-1 kernels between digit and conv 1, layer-2 kernels between pool 1 and conv 2, FC weights and biases between the averages and the softmax), weight columns tinted; three rows: forward (activations and w), backward (the gradient of each, under it), update (w′ = w − lr·∂L/∂w under each weight); channel k is one horizontal line through its kernel, its maps, its average and its row of FC weights. Hover, in green, shows what a value is computed from: an activation's receptive field upstream and the kernel that made its map; a gradient's sources downstream up to the loss and the weights the error came through; a weight in all three rows with the two maps whose product is its gradient. Band 2, Many steps: Play and Restart (new seed, everything cleared), play at 2, 10, 50 or 200 digits a second (default 200), learning rate 0.001 to 0.5 (default 0.1), batch 1, 8 or 32, Restart from edge detectors; loss per digit and its running average; training accuracy over the last 200 digits and held-out accuracy on the 1,000 test digits every 200; layer-1 kernels at 0, 100, 300, 1,000, 3,000 and 10,000 digits; the last 20 digits with their guesses. The maths runs at full speed in a frame loop; the play band redraws ten times a second. While playing, the step band follows: each frame stops with the digit on show at the end of its backward pass, and the band redraws when a new digit is on show, at most ten times a second (about one digit in 20 at 200 a second, every digit at 2). A hovered cell or weight stays probed, so its readout and highlight follow from digit to digit. Pressing Play takes the current digit to the end of its backward pass; Pause leaves it there for Step to update. Design: `docs/superpowers/specs/2026-10-14-cnn-training-layout-design.md`.
- The training page's One-step band has a 2D | 3D switch (remembered in local storage). In 3D one WebGL view shows the same three rows: forward (digit, layer-1 kernels as 3×3×4 with kernels into depth like conv 1's channels, conv 1, pool 1, the eight layer-2 kernels in a 2 × 4 grid with slices into depth like pool 1's channels, conv 2, pool 2, average, FC weights with the biases beneath, softmax), the gradients beneath, and w′ beneath the weights; weight groups framed in the accent colour in every row, and the blocks the last backward step computed framed in green. The same readouts answer a hovered cube, and the highlights are boxes and connectors following the same rules as 2D. A "side by side | depth" switch (remembered) sets the layout; in depth each row runs away from the viewer and the rows become lanes 30 apart, the scores stand beside the FC weights, stages 14 apart with 18 after the averages, and labels that would overlap a nearer one are hidden. Camera presets whole · forward · backward · update frame a complete step's layout by projecting every block's corners, with room for the labels (theta/phi/padding side 0.3/1.2/1.03, 0.35/1.15/1.04, 0.35/1.2/1.03, 0.3/1.2/1.04; depth 0.35/1.05/1.04, 0.55/0.9/1.06, 0.4/1.0/1.05, 0.3/1.0/1.05). Block data are read at draw time, so a new digit is a refresh of colours and sizes, not a rebuild.
- `ui/blocks3d.js` holds the 3D block renderer (scene, instanced cubes, highlight boxes, connectors, labels, orbit camera, picking, render loop) shared by the 3D explorer and the training page; a page declares blocks with rows and positions and keeps its own presets, probes and readouts. Rows stack downwards side by side and become lanes in depth; a block can take another's place along the flow (`at`), set its own depth gap (`gapZ`), shift within its row (`dx`, `dy`), or hold its place without being drawn (`ghost`); `place(defs)` lays blocks out without building them, for camera fits; `declutter` hides labels that would overlap nearer ones; rebuilt meshes are disposed.
- Hand-off: "Use these weights" stores them in local storage (`ui/trained.js`, key `dl-explorer.weights.v1`, with digits seen, passes, held-out accuracy, learning rate, date); the 2D and 3D pages load them at start, show a banner with a "back to the hand-picked kernels" link, and change their "weights are random" wording. "Download JSON" saves the same object.
- Landing page `index.html` ("Visualising AI"): a short lede, chips linking to each architecture with its status, a key to the colour grammar (yellow forward window, green backward trace, blue-to-orange values, dotted terms), then one section per architecture in Alexy's order: CNN (3 pages, as cards), Vision Transformer (next), U-Net, CoAtNet, ConvNeXt (planned). Each section has a schematic of the architecture's shape drawn in SVG by a small script (blocks whose depth is channels, in the pages' colours, light and dark), a one-line definition, the question it asks against its neighbours, and for planned ones what the page will show and what it builds on. Its few terms are explained in the text rather than as dotted tooltips, because the shared glossary would otherwise list every architecture's terms on every page. The three CNN pages carry a breadcrumb back to it. Footer: source link and the MNIST attribution.
- `ui/grid.js` holds the canvas grid drawing and hit-testing (`drawGrid`, `cellAt`, colours, `fmt`, which never prints "-0") shared by the 2D and training pages.
- three.js r128 UMD from cdnjs; OrbitControls is not in that build, so `ui/blocks3d.js` has its own small orbit implementation. External scripts only from cdnjs or jsDelivr, pinned.

### Decisions
- 2026-10-12: The repo lives in a local `repos` folder outside OneDrive, not in the OneDrive project folder. Why: on this laptop, shell tools (git, node, python) cannot write under the synced Documents folder; only Claude's Write/Edit tools can. The OneDrive folder keeps the original zip and a pointer README.
- 2026-10-12: First commit imports the artifact export unchanged, so the pages on `main` are exactly the published artifacts. Why: a clean baseline before the shared-module refactor.
- 2026-10-12: VS Code and Claude Code are opened on the repo, not on the OneDrive folder, from here on. Why: Alexy, after the port ("I'll continue on the proper folder afterwards"); notes and Claude memory live with the repo.
- 2026-10-12: The pages import `core/cnn.js` as ES modules instead of carrying inline copies of the maths. The 2D ReLU toggle and the head probes went into the core (an `activation` option, region probes for `footprint`) rather than staying as page-side copies of the propagation loop. Why: one copy of the maths, and the page wrappers stay a few lines each.
- 2026-10-12: The terms mechanism moved out of the 2D page into a new `ui/` folder (shared DOM code; `core/` stays DOM-free) instead of being copied into the 3D page. Why: the CLAUDE.md rule says reuse it, and step 1 had just removed the other duplicate.
- 2026-10-12: `linkTerms` links each term at its first occurrence, in order of appearance, instead of in `TERMS` order within the text left after the previous match. Why: the old order skipped terms ("receptive field" in the 3D lede came before "kernel" and was never linked); the 2D page gained 11 dotted terms from the change.
- 2026-10-12: The depth-layout default camera looks from the input end, high and nearly head-on, not from the output end looking back (the handoff offered both). Why: from the output end, perspective shrinks the far input and reverses the funnel the lede describes; from high up the funnel reads as a staircase and nothing occludes.
- 2026-10-12: The 2D padding dropdown marks 1 as selected. Why: it showed 0 while the model computed with 1.
- 2026-10-12: Public GitHub repo `Smooth-Cactus0/Visualising-AI`, deployed with GitHub Pages from `main`. The name is Alexy's "Visualising AI" with GitHub's own space-to-hyphen conversion. Why: Pages is free for public repos; a private repo would need a paid plan.
- 2026-10-12: The 2D page's head probes show only their direct link, as the 3D page already did: a global-average entry → its pool-2 map; an FC weight (now hoverable) → its average and its class; a class → the 8 averages and its column of W. Why: Alexy, 2026-10-12: hovering a class lit every upstream map, and hovering an FC weight lit nothing; the artifact-session decision already said the cone is omitted at the head.
- 2026-10-12: Local paths, the Windows username and the IT-policy detail were removed from these notes once the repo was public; the local path lives in Claude's private memory. Commits from this repo now use GitHub's no-reply address. Why: Alexy, 2026-10-12, after the repo went public.
- 2026-10-12: Training page as two stacked bands (One step, Many steps) on one page, chosen over a mode switch and over two columns. Why: Alexy, 2026-10-12: "the step is important but seeing weights being actualised over passes is necessary too"; both must be visible together.
- 2026-10-12: The training page keeps the 16×16 network of the other pages and trains live in the browser with plain SGD, rather than 28×28 or replaying an offline run. Why: the trained weights plug into the 2D and 3D pages, and learning rate and batch stay interactive. The cost, measured: about 80 to 85% held-out, not LeNet's 99%.
- 2026-10-12: Weights drawn as weight · gradient · updated-weight triplets, the arithmetic written out on hover; an arrow overlay is kept in reserve. Why: Alexy chose the triplets in the brainstorm ("might do B depending on final product").
- 2026-10-12: He-uniform initialisation and a default learning rate of 0.1, replacing ±1/√fan_in and 0.05. Why: measured; the first pair learned too slowly (29% after one pass). The brainstorm's guess of 85 to 92% was corrected to the measured 80 to 85% on the page and in the spec.
- 2026-10-12: The early plateau (loss near 2.3 for several hundred digits) is explained on the page, not hidden, and the default play speed is 200 digits a second so it lasts seconds. Why: it is a real property of training from random kernels; the step band is throttled to ten refreshes a second anyway.
- 2026-10-12: The step band freezes while play runs, and the step rows use the full window width and wrap instead of scrolling. Why: Alexy, 2026-10-12, on the deployed page: the step band also played during play, and the horizontal scroll bar hid part of the row when the whole width could show it.
- 2026-10-12: The 3D representation lives on the training page behind a 2D | 3D switch, not on a separate page nor inside the explorer. Why: Alexy chose it ("A") as the closest match to switching representation on the same thing.
- 2026-10-12: The block renderer moved out of the explorer into `ui/blocks3d.js` rather than being copied. Why: one copy; proven unchanged by a scene digest in five states.
- 2026-10-12: Scene rows, forward over gradients over w · ∂L/∂w · w′, side-by-side only. Why: the simultaneous view Alexy chose for 2D, carried into 3D; the depth layout would stack rows on rows.
- 2026-10-12: Equivalence proven by a serialised scene and DOM, not pixels. Why: software WebGL in headless Edge took minutes per screenshot and the eased camera made frame counts matter; the digest is exact, deterministic and takes seconds.
- 2026-10-14: The step band shows each layer's weights where they act, in three rows (forward, backward, update), with the backward pass revealed a layer at a time and framed in green, in 2D and 3D. This replaces separate forward, backward and triplet rows (2D) and five rows (3D). Why: Alexy, 2026-10-14: it should be "clearer where each weights are located" and, "by doing the green contouring, which weights is affected by the loss, and how this is propagating backwards"; in 3D "not very clear which kernel is layer 1 and which are layer 2". The triplet w · ∂L/∂w · w′ survives as the vertical column under each weight.
- 2026-10-14: The 2D line scrolls sideways instead of shrinking to fit. Why: Alexy, 2026-10-14: "We will need a horizontal scroll I believe to have the whole architecture on the same line." This replaces the shrink-to-fit of 2026-10-13.
- 2026-10-14: Green also traces gradients, downstream: hovering a gradient shows the later gradients it was computed from, up to the loss. Why: the same "computed from" meaning as the receptive field, so the backward pass gets the hover the forward pass has.
- 2026-10-14: Reset became Restart, next to Play. Why: Alexy asked for "a restart button to just start anew and clear the plots"; Reset already did this but sat at the end of the controls under another name.
- 2026-10-13: The step band follows play, showing each digit at its backward pass, instead of freezing until pause. Why: Alexy, 2026-10-13: "to be able to see the [3D] representation change when we run the training sequence when we play it"; the backward pass is the one phase where activations, gradients and the coming update are all on show. The freeze of 2026-10-12 answered a different problem (the step band was replaying digits during play) and the redraw stays throttled.
- 2026-10-13: The depth layout came to the training 3D view with rows as lanes side by side, not stacked. Why: Alexy asked for the depth layout there too; stacked rows would hide each other from the high camera the depth layout needs (the reason it was left out on 2026-10-12).
- 2026-10-13: Camera presets frame a complete step's layout rather than the rows present. Why: switching to 3D before the backward pass fitted the camera to two rows and cut off the gradient rows when they appeared, which live play makes the common case.
- 2026-10-13: The forward and backward rows stay on one line by shrinking their grids, down to half size, instead of wrapping the last stages under the row. Why: Alexy, 2026-10-13: the softmax landing under the forward pass "makes it hard to read". This replaces the wrap of 2026-10-12, which had replaced a sideways scroll.
- 2026-10-13: Architectures, in order: CNN (built), Vision Transformer, U-Net (encoder–decoder), CoAtNet, ConvNeXt. Why: Alexy, 2026-10-13: "We will do a visual transformer, we will do a UNET, so encoder decoder, we will do [CoAtNet] and [ConvNeXt]", and the ViT next.
